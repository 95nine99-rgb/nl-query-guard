# 회고

## 무엇을 만들었나

자연어 질의를 SQL 로 바꿔 실행하되, **LLM 이 만든 SQL 을 그대로 믿지 않는 구조**를 만들었다.

```
질문 → 프롬프트 조립 → LLM → 검증·user_id 주입 → 읽기전용 실행 → 결과
                              ↑ 거부되면 최대 2회 재생성
```

---

## 이 프로젝트에서 가장 중요한 판단 3개

### 1. 파서를 짜기 전에 먼저 뚫어봤다

방어 코드를 짜기 전에 악의적 SQL 12종을 실행했다. 결과가 예상과 달랐다.

**읽기 전용 계정 하나로 12종 중 8종이 막혔다.** 파서는 한 줄도 없었다.
뚫린 4종은 전부 `transactions` 를 `SELECT` 하는 **정상 요청**이었다.

> DB 는 "무엇을" 만 안다. "누구 것인지" 는 앱만 안다.

**파서가 막아야 할 범위가 12개가 아니라 4개로 좁혀졌다.**
먼저 짰으면 12개를 다 막는 복잡한 것을 만들었을 것이다. **측정이 설계를 바꿨다.**

### 2. 정규식과 파서를 둘 다 만들어 비교했다

같은 테스트 7개로 재니 **통과 수는 4:4 로 같았다.** 여기서 멈췄으면 정규식을 골랐을 것이다.

**실패의 성격이 달랐다.**

| | 정규식 | 파서 |
|---|---|---|
| 실패 A | 문자열 리터럴의 `--` 를 잘라 **SQL 파손** | `user_id=1 AND user_id=2` → **0건** |
| 실패 B | 소문자 `where` 를 못 잡아 **정상 요청 거부** | 정책 차이 |

**정규식은 망가지고 파서는 보수적으로 동작한다.** 같은 숫자가 같은 의미가 아니다.

결정적인 것은 고치는 난이도였다. **정규식이 문자열 리터럴 안인지 구분하려면 결국 파싱이 필요하다.**
정규식으로 정규식의 한계를 넘을 수 없다.

### 3. `user_id` 는 검사하지 않고 강제로 덮어쓴다

검사 방식은 위험 패턴을 전부 알아야 한다. `user_id=2` · `IN(1,2)` · `!=1` · `OR 1=1` …
**하나만 빠뜨려도 뚫린다.**

주입 방식은 LLM 이 무엇을 쓰든 상관없다. 서버가 `WHERE user_id = 1 AND (...)` 로 덮어쓴다.

> 막을 것을 나열하지 않는다. 허용할 것을 강제한다.

같은 원칙이 세 곳에 반복된다.

- MySQL `GRANT` — 테이블을 하나씩 명시한다. `nlquery.*` 를 쓰지 않는다
- `instanceof Select` — `DROP|DELETE|UPDATE|...` 를 나열하지 않는다
- `user_id` 주입 — 위험 패턴을 나열하지 않는다

## 예상과 달랐던 것

### 옵티마이저가 내가 만든 인덱스를 쓰지 않았다

복합 인덱스를 만들고 `ANALYZE TABLE` 까지 했는데 `EXPLAIN` 이 다른 인덱스를 골랐다.
`EXPLAIN` 만 봤으면 **"인덱스가 소용없다"** 고 결론 낼 뻔했다.

`FORCE INDEX` + `EXPLAIN ANALYZE` 로 실측하니 읽는 행이 **995 → 20**, `Sort` 단계가 사라졌다.

원인은 **시드 유저가 3명이라 `user_id` 카디널리티가 3** 이었기 때문이다.
**측정 환경이 결론을 뒤집었다.**

### LLM 이 내 공격 목록의 한계를 드러냈다

모델이 자연스럽게 만든 SQL 이 이랬다.

```sql
WHERE amount > 30000 AND category_id IN (SELECT id FROM categories WHERE name = '쇼핑')
```

`InExpression` 은 `BinaryExpression` 이 아니라 AST 재귀에서 빠졌다.
`WHERE user_id IN (SELECT 2)` 가 탐지를 통과했다.

**직접 짠 악의적 SQL 12종에는 `IN` 도 `BETWEEN` 도 없었다.**
책상에서 만든 목록보다 실제 사용이 넓었다. **LLM 을 붙여보고서야 드러났다.**

그리고 그 재귀는 **타입을 아는 것만 검사하고 모르면 통과시키는 블랙리스트**였다.
같은 파일의 `instanceof Select` 는 화이트리스트인데 **방식이 섞여 있었다.**

## 측정 도구를 세 번 의심해야 했다

| # | 무엇 | 만약 그대로 기록했다면 |
|---|---|---|
| 1 | 파괴형 테스트(`DROP`)를 먼저 실행 | 이후 전부 `TABLE_NOT_FOUND`. **차단율 92% 가짜 결과** |
| 2 | 낡은 기준의 정상 질의로 오탐 측정 | **"우리 검증기는 정상 질의를 전부 막는다"** |
| 3 | 프롬프트 예시에 있는 질의로 모델 성능 측정 | 출력이 예시와 글자 하나 다르지 않았다. **복사를 생성으로 착각** |

세 번 다 **측정 대상이 아니라 측정 도구가 문제**였다.

`docs/04-experiment.md` 에 **"측정 전에 설계를 쓴다"** 를 지킨 덕에 1번을 잡았다.
`maxRows=200` 상한 때문에 행 수만으로는 방어 여부를 판정할 수 없다는 것도 뒤늦게 알았다.

## 남은 과제

| | 내용 | 왜 안 했나 |
|---|---|---|
| **방어층 2 — 테이블 화이트리스트** | `TablesNamesFinder` 로 참조 테이블을 뽑아 허용 목록과 대조 | 시간. 30분이면 된다 |
| **`information_schema` 차단은 우연이다** | 해당 테이블에 `user_id` 컬럼이 없어 주입된 SQL 이 깨진 것 | **의도한 방어가 아니다.** `user_id` 를 가진 테이블이 생기면 성질이 사라진다 |
| `user_id` 조건 제거 방식 | 현재는 거부 + 재생성. 제거 후 주입이 오탐을 더 줄인다 | AST 순회 필요. 시간 |
| 문자열 리터럴 오탐 | `WHERE title = 'user_id 관련 지출'` 이 차단된다 | 현재 도메인에서 발생 확률이 낮다고 판단해 감수 |
| 의도 분류 · 신뢰도 임계값 | 원래 계획에 있었다 | **Ollama 는 confidence 를 주지 않는다.** 재생성 횟수로 대체 |
| 프롬프트 회귀 CI | 정답셋 30건 + `PromptRegressionTest` | **빨간 CI 는 아무것도 막지 못하므로** 구현 전까지 수동 실행으로 꺼뒀다 |
| Testcontainers | 로컬·CI 동일 동작 | 학습 비용. P2 에서 도입 후 ADR-004 supersede |
| Spring AI | 프로바이더 교체가 쉬워진다 | **포트를 직접 만들어보는 것이 먼저**라고 판단 |
| 응답의 SQL 노출 | `rawSql` · `executedSql` | **데모 목적**이다. 운영이면 내부 스키마가 새어 나간다 |
| 질의 로그 조회 API | 테이블은 있으나 API 가 없다 | 우선순위 |
| 전역 예외 핸들러 | 예상 못 한 예외가 스택트레이스로 나갈 수 있다 | 시간 |

## 이 프로젝트에서 안 한 것과 그 이유

**시드를 최근 3개월치로 늘리지 않았다.**
2026-08 한 달치 5,000건으로 고정했다. 늘리면 8/31·9/02 의 측정값(1,632건 등)과 어긋난다.
**측정 일관성을 택했다.** 대신 "이번 달" 질의는 0건이 나온다.

**인증을 만들지 않았다.**
`loginUserId` 는 `NlQueryController` 에 상수 `1L` 이다.
이 프로젝트의 주제는 인증이 아니라 **"인증된 사용자의 경계를 어떻게 강제하는가"** 다.

## 다음에 다르게 할 것

**계획을 실제 가용 시간으로 세운다.**
"하루 6~8시간 매일" 로 시작했으나 실제는 주 2~3일이었다. **네 번 재조정했다.**
범위를 자르지 않고 날짜를 미는 쪽을 택한 것은 맞았다고 본다. 다만 첫 계획이 현실과 너무 멀었다.

**라이브러리를 처음 쓸 때 클래스 지도를 먼저 만든다.**
JSQLParser 의 `Statement` · `PlainSelect` · `Expression` · `BinaryExpression` 이
SQL 의 어느 부분에 대응하는지 몰라 오래 헤맸다. 자바 개념을 몰라서가 아니었다.

**AST 순회는 타입을 나열하지 않는다.**
`Expression` 하위 타입은 수십 개다. 처음부터 파싱 결과를 문자열로 훑거나
파서가 제공하는 방문자를 썼어야 했다.
