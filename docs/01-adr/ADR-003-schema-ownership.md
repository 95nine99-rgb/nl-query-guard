# ADR-003 · 스키마를 누가 소유하는가

- 상태: **채택**
- 날짜: 2026-08-25
- 관련 브랜치: `feat/domain-and-query-api`

## 결정

**SQL 스크립트가 스키마의 단일 진실이다. Hibernate 는 `ddl-auto=validate` 로 검증만 한다.**

## 맥락

Spring Initializr 기본값은 `ddl-auto=update` 였다. 엔티티를 쓰면 테이블이 자동으로 생겨 편하다.
그런데 `update` 는 **추가만 하고 삭제·변경은 하지 않는다.**

| 내가 한 일 | `update` 의 동작 |
|---|---|
| 필드 추가 | 컬럼 추가 |
| 필드 삭제 | **아무것도 안 함** — 컬럼이 그대로 남음 |
| 타입 변경 | **아무것도 안 함** |
| 인덱스 삭제 | **아무것도 안 함** |

시간이 지나면 엔티티와 실제 테이블이 조용히 어긋난다.

## 검토한 대안

| 대안 | 판단 | 이유 |
|---|---|---|
| `ddl-auto=update` | 버림 | 오늘 가장 빠르다. 하지만 **8/26 인덱스 실험이 불가능해진다** — 인덱스를 뺐다 넣었다 해야 하는데 `update` 는 인덱스를 지우지 않는다. 실험 통제가 깨진다 |
| `ddl-auto=create` | 버림 | 매번 초기화되어 통제는 되지만 시드 5천 건을 매번 다시 넣어야 한다. 그리고 실수로 운영에서 켜면 데이터가 날아간다 |
| **SQL 스크립트 + `validate`** | **채택** | 인덱스를 `CREATE INDEX` / `DROP INDEX` 로 정확히 통제한다. ERD 문서와 실제 스키마가 일치한다. 엔티티가 스키마와 어긋나면 **앱이 아예 안 뜬다** |
| Flyway / Liquibase | 조건부 | 마이그레이션 버전 관리까지 된다. 2주 프로젝트에 도입 비용이 크고, 지금은 스키마 변경이 잦지 않다. **환경이 2개 이상 되거나 스키마 변경이 반복되면 그때 도입** |

## 선택 이유

**1. 8/26 인덱스 실험이 이 결정에 걸려 있다.**
복합 인덱스를 걸고 EXPLAIN before/after 를 잰다. `update` 로는 인덱스를 되돌릴 수 없어 "인덱스 없는 상태" 를 재현하지 못한다.
측정이 주제인 프로젝트에서 **측정 대상을 통제할 수 없는 설정**을 고를 수는 없다.

**2. 운영에서 `ddl-auto=update` 는 금기다.**
Hibernate 가 예상하지 못한 DDL 을 날릴 수 있다. P2 에서 배포를 다루면서 로컬은 `update` 를 쓰는 건 앞뒤가 맞지 않는다.

**3. 인덱스 설계 근거가 문서에 남는다.**
`docs/03-erd.md` 의 인덱스 표와 `infra/schema.sql` 이 1:1 로 대응한다.
`@Index` 어노테이션으로 흩어져 있으면 "왜 이 순서인지" 를 한눈에 볼 수 없다.

## 대가 (알고 선택했다)

- 엔티티를 고칠 때마다 SQL 도 같이 고쳐야 한다. **한쪽만 고치면 `validate` 가 앱 기동을 막는다**
- 초기 설정에 30분이 더 든다
- 스키마 변경 이력이 git diff 로만 남는다 (Flyway 처럼 버전 테이블이 없다)

**세 번째가 실제 한계다.** 스키마 변경이 잦아지면 Flyway 로 넘어간다.

## 함께 내린 결정 2개

### FK 제약을 실제로 건다

대용량 서비스에서는 FK 를 빼기도 한다 — 락 경합, 샤딩 불가, 배치 삭제 시 성능 때문이다.
**하지만 그건 트래픽 규모 때문에 포기하는 것이지 더 나은 설계라서가 아니다.**

이 프로젝트는 건다:
- 5천 건 규모에 FK 성능 문제가 생길 리 없다
- **`user_id` 참조 무결성이 이 프로젝트의 주제다.** "남의 데이터를 못 보게 한다" 가 핵심인데 DB 레벨 보장을 스스로 빼는 건 앞뒤가 맞지 않는다
- FK 가 만드는 단일 인덱스가 8/26 실험의 **before 조건**이 된다

### `transaction_at` 은 `DATETIME` (`TIMESTAMP` 아님)

| | `DATETIME` | `TIMESTAMP` |
|---|---|---|
| 저장 | 입력값 그대로 | UTC 로 변환 |
| 범위 | 1000~9999년 | **1970~2038년** |

- `transaction_at` 은 **거래가 일어난 시각**, 즉 비즈니스 데이터다
- `application.properties` 에 `serverTimezone=Asia/Seoul` 이 있다. `TIMESTAMP` 면 이 설정 하나에 과거 데이터 해석이 달라진다
- **자연어 질의로 "이번 달" 을 계산하는데 그 기준이 흔들리면 안 된다**
- 2038년 문제도 있다

## 되돌릴 조건

- 스키마 변경이 주 3회를 넘어가면 → Flyway 도입
- 환경이 2개 이상(로컬 + 스테이징)이 되면 → Flyway 도입
