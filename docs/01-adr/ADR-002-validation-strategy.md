# ADR-002 · 생성된 SQL을 무엇으로 검증할 것인가

- 상태: **검토 중** (실측 완료, 결정 미정)
- 날짜: 2026-08-31
- 관련 브랜치: `feat/sql-validator`

## 결정 (한 줄)

> 미정. **다만 결정에 필요한 수치는 확보했다.** 아래 "측정 결과" 참조.

## 맥락

**게이트 질문 ②의 답이 이 문서에서 나온다.**
"내 화이트리스트를 우회하는 SQL을 하나 만들어봐라. 못 만들겠으면 왜 못 만드는지 설명해라."

## 방어를 몇 겹으로 둘 것인가

| 층 | 막는 것 | 어디서 | 무력화 가능? |
|---|---|---|---|
| 1 | `SELECT` 외 구문 · 다중 구문 | 앱 (파서) | 내 코드 → 가능 |
| 2 | 허용 밖 테이블·컬럼 | 앱 (파서) | 내 코드 → 가능 |
| 3 | `user_id` 서버 강제 주입 | 앱 (코드) | 내 코드 → 가능 |
| 4a | 변경 구문 | 앱 (JDBC `readOnly`) | 한 줄로 가능 |
| **4b** | **권한 밖 접근** | **DB (MySQL GRANT)** | **불가능** |
| 4c | 결과 과다 · 장시간 | 앱 (`maxRows`, `queryTimeout`) | 가능 |

**4b 만 내 코드 밖에 있다.** 나머지는 전부 내가 실수할 수 있는 영역이다.

> 8/31 실측에서 4a 와 4b 가 별개로 동작한다는 것이 드러났다.
> `DROP` 을 `query_ro` 로 실행했을 때 4b(MySQL 권한)가 아니라 **4a(JDBC readOnly)가 먼저 잘랐다.**
> "막혔다" 로 끝내면 어느 층이 막았는지 모른다.

## 측정 결과 (2026-08-31) — `docs/05-result.md` 6절

파서를 짜기 **전에** 12종을 실행했다.

| 계정 | 차단 |
|---|---|
| `app` (전체 권한) | **2 / 12** |
| `query_ro` (읽기 전용) | **8 / 12** |

### 여기서 나온 사실 3개

**① 파서 0줄로 8종이 막힌다.** 읽기 전용 계정 하나로.

**② 뚫린 4종은 DB 가 구조적으로 막을 수 없다.**
5·7·11 은 `transactions` 를 `SELECT` 하는 정상 요청이다. **DB 는 "누구 것인지" 를 모른다.**
8은 `information_schema` 라 GRANT 와 무관하다.

**③ 차단된 것 중 2개는 내 방어가 아니다.**
4번(다중 구문)은 JDBC `allowMultiQueries=false` 기본값,
12번(주석 분할)은 MySQL 파서가 `SEL/**/ECT` 를 키워드로 인식하지 않아서 막혔다.
**기본값이 바뀌면 그대로 열린다. 내 성과로 적으면 안 된다.**

## 검토한 대안

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 정규식 간이 검증 | 빠르다 | 대소문자·주석·인코딩 우회 | 미정 |
| JSQLParser AST 검사 | 구조를 정확히 본다 | 학습 곡선, 버전 의존 | 미정 |
| LLM 재검증 | 구현이 쉽다 | **검증자도 못 믿는다.** 비용·지연 2배 | **버림** |
| 실행 계층 방어 (읽기전용 계정·row limit·timeout) | 파서를 뚫려도 막힘 | 설정 관리 필요 | **채택 (측정으로 8/12 확인)** |

## 남은 판단

**① 정규식 vs JSQLParser** — 전제가 바뀌었다.
파서가 단독으로 책임질 것은 **8번(허용 밖 테이블) 하나**다.
5·7·11 은 방어층 3(`user_id` 주입)이 담당한다.
"12종을 다 막는 검증기" 가 아니라 "테이블 참조만 잡는 검증기" 라면 요구 수준이 다르다.

**② DB 권한 하나에 8종을 걸어둘 것인가**
2026-08-27 시점에 `query_ro` 는 `GRANT USAGE` 뿐이었다(스크립트 미실행).
**그 상태였다면 8종이 전부 열려 있었다.**
설정 하나가 방어의 3분의 2를 좌우한다면, 앱 계층에 중복으로 둘 것인지 판단이 필요하다.

## 되돌릴 조건

- 파서가 정상 질의를 막기 시작하면(오탐 발생) 검증 강도를 낮추고 실행 계층 방어를 두껍게 한다
- `query_ro` 권한이 검증 없이 변경될 수 있는 구조면(CI/배포에서) 앱 계층 중복 검증을 필수로 올린다

## 2026-09-01 추가 — 정규식 vs JSQLParser 실측

**결정 방식**: 추측하지 않고 **둘 다 만들어서 같은 테스트 7개를 돌렸다.**
`UserIdEnforcer` 인터페이스로 받아 구현만 갈아끼웠다.

| | 정규식 | JSQLParser |
|---|---|---|
| 통과 | 4 / 7 | 4 / 7 |
| 실패의 성격 | **SQL 파손 · 오탐** | 0건 반환 · 정책 차이 |
| 분기 수 | if 3 + replaceAll 2 | if 2 |
| 새 변형이 나오면 | 분기가 늘어난다 | 늘지 않는다 |

전체 표와 케이스별 결과는 `docs/05-result.md` 8절.

### 결정: **JSQLParser 를 채택한다**

숫자가 4:4 로 같은데도 파서를 고르는 이유는 셋이다.

**① 실패했을 때 피해가 다르다**
정규식은 문자열 리터럴 안의 `--` 를 잘라 **SQL 자체를 부쉈다**(케이스 E).
소문자 `where` 를 못 잡아 **정상 요청을 거부했다**(케이스 G, 오탐).
파서의 실패는 `user_id=1 AND user_id=2` → **0건 반환**이다. 데이터가 새지 않는다.

**② 정규식 E 는 고칠 수 없다**
문자열 리터럴 안인지 SQL 구조인지 구분하려면 **결국 파싱이 필요하다.**
정규식으로 정규식의 한계를 넘을 수 없다.

**③ 유지보수 비용이 반대 방향이다**
오늘 정규식 버전은 변형을 하나 발견할 때마다 분기가 하나씩 늘었다
(`\s*` → 주석 제거 → user_id 유무 분기 → 문자열 리터럴은 포기).
파서는 `parse()` 한 번으로 공백·대소문자·주석 변형이 전부 사라진다.

### 버린 대안과 이유

| 대안 | 판단 | 이유 |
|---|---|---|
| 정규식 간이 검증 | **버림** | E(SQL 파손)를 고치려면 파싱이 필요하다. 근본 해결 불가 |
| JSQLParser AST 검사 | **채택** | 실패해도 보수적으로 동작한다. 방어층 1(SELECT only)이 `instanceof Select` 한 줄로 해결된다 |
| LLM 재검증 | **버림** | 검증자도 못 믿는다. 비용·지연 2배 |
| 실행 계층 방어 | **채택 (병행)** | 8/31 측정에서 파서 0줄로 12종 중 8종을 막았다 |

### 부수 효과 — 방어층 1이 한 줄이 됐다

```java
if (!(stmt instanceof Select)) throw new SqlGuardException("SELECT 가 아니다");
```

정규식이었다면 `DROP|DELETE|UPDATE|INSERT|TRUNCATE|ALTER|...` 를 나열해야 했다.
**빠뜨리면 뚫린다.** 파서는 "SELECT 인가" 만 물으면 나머지가 자동으로 거부된다.
막을 것을 나열하는 대신 허용할 것을 지정하는 구조다.
