# ADR-002 · 생성된 SQL을 무엇으로 검증할 것인가

- 상태: 제안
- 날짜: 2026-08-27 (예정)
- 관련 브랜치: `feat/sql-validator`

## 결정 (한 줄)

> 착수 후 채운다.

## 맥락

**게이트 질문 ②의 답이 이 문서에서 나온다.**
"내 화이트리스트를 우회하는 SQL을 하나 만들어봐라. 못 만들겠으면 왜 못 만드는지 설명해라."

## 검토한 대안

| 대안 | 판단 | 장점 | 단점 | 버린 이유 |
|---|---|---|---|---|
| 정규식 간이 검증 | | 빠르게 만든다 | 대소문자·주석·인코딩 우회가 쉽다 | |
| JSQLParser 파싱 후 AST 검사 | | 구조를 정확히 본다 | 학습 곡선, 파서 버전 의존 | |
| LLM에게 재검증 시킨다 | | 구현이 쉽다 | **검증자도 못 믿는다**. 비용·지연 2배 | |
| 위 + 실행 계층 방어(읽기전용 계정·row limit·timeout) | | 파서를 뚫려도 마지막에 막힘 | 설정 관리 필요 | |

## 방어를 몇 겹으로 둘 것인가

1. 구문 검증 — SELECT only, 다중 구문 금지
2. 스키마 검증 — 허용 테이블·컬럼 화이트리스트
3. 권한 — `user_id`를 **서버가 강제 주입** (타협 불가)
4. 실행 — 읽기 전용 DB 계정 + row limit + 쿼리 타임아웃
