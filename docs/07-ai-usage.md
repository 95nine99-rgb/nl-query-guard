# AI 사용 기록 · 툴체인 결정

이 프로젝트의 주제는 "AI 출력을 백엔드가 검증한다"이다.
개발 과정에도 같은 원칙을 적용한다. **AI가 코드를 빨리 짜주는 건 전제이고, 무엇을 짜라고 지시할지가 실력이다.**

---

## 1. 원칙

| | 예시 |
|---|---|
| 하지 않는다 | "Text2SQL 검증 레이어 만들어줘" — 무엇을 만들지 내가 모르는 상태 |
| 한다 | "SELECT only + 허용 테이블 화이트리스트로 검증하는 Validator를 만들어줘. 인터페이스는 `validate(String sql) → ValidationResult`" — **설계는 내가, 타이핑은 AI** |
| 한다 | "내가 짠 이 파서가 뚫릴 케이스 5개를 공격자 입장에서 만들어봐" |
| 한다 | "이 두 방식의 트레이드오프를 표로 정리해줘. 결정은 내가 한다" |

**핵심**: AI에게 넘기는 건 구현이고, 절대 안 넘기는 건 **판단**이다.
무엇을 통과시킬지 · 임계값을 얼마로 할지 · 어느 방어층을 몇 겹 둘지.

## AI가 그럴듯하게 틀린 사례

### 1. `SEL/**/ECT` 주석 분할 우회 (2026-08-31)

**AI 주장**: 악의적 SQL 12종에 "주석 분할 우회" 를 넣자며 이렇게 제시했다.

```sql
SEL/**/ECT * FROM transactions
DR/**/OP TABLE transactions
```

"정규식 검증을 확실히 뚫는 실물" 이라고 설명했다.

**실제**: **MySQL 에서 아예 동작하지 않는다.** 키워드 중간에 주석을 넣으면 그냥 문법 오류다.
`app` 계정에서도 `query_ro` 에서도 `SQL_ERROR` 로 차단됐다.

**교훈**: 실행해보지 않은 공격 패턴을 표에 넣으면 **"12종 전부 차단" 이 부풀려진다.**
차단된 것이 내 방어 덕분인지, 애초에 동작하지 않는 것인지 구분해야 한다.

### 2. DataSource 빈을 하나만 정의 (2026-08-31)

**AI 코드**: `query_ro` 용 DataSource 만 `@Bean` 으로 만들었다. 컴파일도 통과했다.

**실제**: 기동 시 `SchemaManagementException`. Spring Boot 의 DataSource 자동 설정은
`@ConditionalOnMissingBean` 이라 **DataSource 를 하나라도 직접 만들면 자동 설정 전체가 물러난다.**
`app` 계정 DataSource 가 생성되지 않아 JPA 가 `query_ro` 로 스키마를 검증하다 실패했다.

**같은 실수를 `JdbcTemplate` 에서 한 번 더 반복했다.**
`queryJdbcTemplate` 을 정의하자 `JdbcTemplateAutoConfiguration` 이 물러나 기본 빈이 사라졌다.

**교훈**: "내 것만 추가되고 기본은 남는다" 가 아니다. 같은 타입 빈을 직접 만들면 그 자동 설정이 통째로 비활성화된다.
그리고 **`ddl-auto=validate` 였기 때문에 기동 즉시 드러났다**(ADR-003). `update` 였다면 조용히 이상하게 동작했을 것이다.

### 3. 측정 순서 설계 실패 (2026-08-31)

**AI 스크립트**: 공격 12종을 1번(`DROP`)부터 순서대로 실행하게 짰다.

**실제**: 1번에서 테이블이 사라져 2~9번이 전부 `TABLE_NOT_FOUND` 로 나왔다.
**이걸 "차단" 으로 읽었으면 차단율 92% 라는 가짜 결과가 나왔다.**

**교훈**: 파괴적 테스트는 다른 측정을 오염시킨다. 비파괴를 먼저, 파괴는 마지막에, 매번 복구.
`04-experiment.md` 에 "통제 변수: 동일 시드 데이터" 를 **미리 적어둔 덕에** 잡아냈다.

### 4. 테스트 기대값을 출력 형식에 묶었다 (2026-09-01)

**AI 제안**: `assertThat(actual).contains("user_id=1")`

**실제**: 정규식 구현에서 파서 구현으로 갈아끼우자 **7개 중 4개가 한꺼번에 실패**했다.
기능은 정상인데 파서가 `user_id = 1`(공백 포함)로 렌더링해서 문자열이 안 맞았다.

**교훈**: 두 구현을 같은 테스트로 비교하려면 검증이 **출력 형식에 의존하면 안 된다.**
공백을 제거해 형태가 아닌 내용만 비교하도록 바꿨다.

### 5. 가짜 통과를 만들 뻔했다 (2026-09-01)

**AI 제안**: A 케이스에 `doesNotContain("user_id = 2")` (공백 포함)

**실제**: 검증 대상은 공백을 제거한 문자열이라 **이 검사는 절대 실패하지 않는다.**
아무것도 검증하지 않으면서 초록불이 떴다.

공백을 뺀 `"user_id=2"` 로 고치자 A 가 실패로 바뀌었다.
**실패가 늘어난 것이 정직해진 것이다.**

### 6. 사수가 코드를 대신 썼다 (2026-09-01)

`JsqlUserIdEnforcer` 를 만들 때 사수가 완성 코드를 줬다.
`WORKING-AGREEMENT.md` 3조("메서드 본문을 대신 쓰지 않는다") 위반이다.

사용자가 자바 기초를 모른다고 오판한 것이 원인이었다.
실제로는 **JSQLParser 클래스가 무엇을 나타내는지 지도가 없었던 것**이다
(`Statement`, `PlainSelect`, `Expression` 이 SQL 의 어느 부분인지).

→ 라이브러리를 처음 쓸 때는 **클래스 = SQL 의 무엇** 대응표를 먼저 준다.
   용어 정의가 아니라 그림과 비유부터. (`AGENTS.md` 에 규칙 등록)

### 7. AST 재귀로 user_id 를 찾으려다 구멍을 냈다 (2026-09-02)

**AI 제안**: `Expression` 타입을 재귀로 순회해 `user_id` 컬럼을 찾는다.

```java
if (expr instanceof Column c)           return "user_id".equalsIgnoreCase(...);
if (expr instanceof BinaryExpression b) return 좌 || 우;
return false;
```

교과서적으로 보였다. AST 를 다루면 타입별 순회가 정석이니까.

**실제**: **LLM 이 자연스럽게 만든 SQL 이 구멍을 드러냈다.**

```sql
SELECT * FROM transactions
WHERE amount > 30000 AND category_id IN (SELECT id FROM categories WHERE name = '쇼핑')
```

`InExpression` 은 `BinaryExpression` 이 아니라 마지막 `return false` 로 빠진다.
확인해보니 `WHERE user_id IN (SELECT 2)` 가 그대로 통과했다.
`Between` · `NotExpression` · `Parenthesis` 도 같은 이유로 빠진다.

**교훈 2개**

**① 타입을 나열하는 것은 블랙리스트다.**
정규식에서 변형을 하나씩 막다가 실패한 것과 같은 구조다.
이 프로젝트가 채택한 "막을 것을 나열하지 말고 허용할 것을 지정한다" 원칙과도 반대다.
`Expression` 하위 타입은 수십 개라 애초에 나열이 불가능했다.

**② 인위적 공격 목록보다 실제 사용이 넓었다.**
8/31 에 직접 짠 악의적 SQL 12종에는 `IN` · `BETWEEN` 이 없었다.
책상에서 만든 목록의 한계다. **LLM 을 붙여보고서야 드러났다.**

→ 파싱이 끝난 표현식을 문자열로 검사하도록 바꿨다.
   주석·공백·대소문자는 파서가 이미 정규화했으므로 안전하고, 어느 타입에 숨어도 놓치지 않는다.
   문자열 리터럴 오탐이라는 한계는 코드 주석과 `06-retro.md` 에 남겼다.

### 8. 프롬프트 예시에 있는 질의로 성능을 측정할 뻔했다 (2026-09-02)

**AI 제안**: 프롬프트 파일을 읽어 `{{QUERY}}` 에 "가장 비싼 거래 5건" 을 넣고 결과를 확인한다.

**실제**: 출력이 프롬프트 예시와 **글자 하나 다르지 않았다.**

```
프롬프트 예시: 질의: 가장 비싼 거래 5건
              SQL: SELECT title, amount, transaction_at FROM transactions ORDER BY amount DESC LIMIT 5
실제 출력:          SELECT title, amount, transaction_at FROM transactions ORDER BY amount DESC LIMIT 5
```

**모델이 생성한 것이 아니라 예시를 베낀 것이다.** 이대로 "3B 모델로 충분하다" 고 결론 낼 뻔했다.

예시에 없는 질의("3만원 넘게 쓴 거래 중에 쇼핑 카테고리만")로 다시 물었더니
서브쿼리를 쓰고 `SQL:` 접두사를 붙이는 등 실제 동작이 드러났다.

**교훈**: few-shot 프롬프트를 평가할 때 **예시에 포함된 질의로 재면 안 된다.**

### 9. 프롬프트 설계 실수로 접두사가 붙었다 (2026-09-02)

프롬프트 마지막 줄을 `SQL:` 로 끝냈더니 모델이 출력에도 `SQL: ` 을 붙였다.

```
SQL: SELECT * FROM transactions WHERE amount > 30000 ...
^^^^^ 이대로 JSQLParser 에 넣으면 파싱 실패
```

규칙 5에 "SQL 만 출력한다" 고 적어뒀는데도 형식을 따라했다.
**프롬프트의 지시문보다 형식이 더 강하게 작용한다.**

### 10. 첫 호출부터 규칙을 어겼다 (2026-09-02)

프롬프트 규칙 4: "세미콜론을 쓰지 않는다"
첫 테스트 출력: `... ORDER BY amount DESC LIMIT 5;`

**프롬프트는 계약이지 보장이 아니다.** Enforcer 가 필요한 이유가 1회차에 실물로 나왔다.
