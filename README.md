# 거래내역 자연어 검색 백엔드 — Text2SQL 검증 및 안전 실행

> **LLM은 자연어를 SQL로 그럴듯하게 바꾼다. 그런데 그 SQL이 DROP인지, 남의 데이터를 훑는지는 모델이 판단할 수 없다.**
> 무엇을 실행시킬지 정하는 판단 레이어를 만든 프로젝트다.

## 3줄 요약

| | |
|---|---|
| **문제** | LLM이 생성한 SQL을 그대로 실행하면 데이터가 오염되거나 남의 데이터가 새어나간다 |
| **대안** | 정규식 검증 / LLM 재검증 / **파서 + 화이트리스트 + 실행계층 방어 4겹** (→ [ADR-002](docs/01-adr/ADR-002-validation-strategy.md)) |
| **결과** | *(측정 후 채움)* 악의적 SQL 12종 차단율 `-` → `-`, 정상 질의 오탐 `-`건 |

## 실행법

```bash
git config core.hooksPath .githooks   # 비밀 커밋 차단 훅 (리포당 1회)
docker compose up -d                  # MySQL 8.0
./gradlew bootRun             # 앱 (기본 LLM 모드 = mock)
```

```bash
curl -X POST localhost:8080/api/queries \
  -H 'Content-Type: application/json' \
  -d '{"text":"이번 달 카페에서 얼마 썼어?"}'
```

## 이 프로젝트를 만든 방식 — 먼저 깨뜨리고, 그다음에 막는다

1. **1주차엔 LLM을 쓰지 않았다.** 규칙 기반(키워드 매칭)으로 파이프라인 전체를 먼저 완성했다.
2. **방어 없이 먼저 뚫려봤다.** `거래내역 전부 지워줘`를 실행해 테이블을 직접 날렸다. → [스크린샷](docs/05-result.md)
3. 그다음에 화이트리스트 파서를 만들었다.
4. **2주차에 규칙이 깨지는 자리에만 LLM을 끼웠다.** 어디서 깨졌는지는 [실패 질의 목록](docs/eval-cases.md)에 있다.
5. 프롬프트를 바꿀 때 정확도가 떨어지면 [CI가 머지를 막는다](.github/workflows/prompt-regression.yml).

## 방어 4겹

| 층 | 무엇 | 뚫리면 |
|---|---|---|
| 1 | 구문 검증 — SELECT only, 다중 구문 금지 | 2층으로 |
| 2 | 스키마 검증 — 허용 테이블·컬럼 화이트리스트 | 3층으로 |
| 3 | 권한 — `user_id`를 **서버가 강제 주입** (타협 불가) | 4층으로 |
| 4 | 실행 — 읽기 전용 DB 계정 + row limit + 타임아웃 | — |

## 출처

이 프로젝트는 카카오페이 기술블로그의 두 사례에서 출발했다.

| | 원문에서 가져온 것 | 이 프로젝트에서 새로 한 것 |
|---|---|---|
| Text2SQL 파이프라인 | 의도 분류 → Entity 추출 → SQL 생성 → SQL 검증 **4단계 구조**, `SELECT` 구조를 고정하고 **WHERE 조건만 LLM이 채우는** 방식 | **파서 기반 화이트리스트 검증층**, 읽기 전용 DB 계정 + row limit + 타임아웃, `user_id` 서버 강제 주입 |
| 문서 파싱 검증 | 모델 **confidence 임계값** + **편집거리(레벤슈타인) 보정**으로 오인식 처리 | 임계값 미달 시 실행 대신 **되묻기**, 임계값 구간별 정확도-통과율 곡선, **프롬프트 회귀 테스트 CI** |

원문은 LLM이 생성한 SQL을 **다시 LLM으로 재검증**했다.
이 프로젝트는 거기서 한 걸음 더 갔다 — **검증자도 LLM이면 그 검증은 왜 믿는가**.
그래서 검증을 모델이 아니라 **파서와 화이트리스트라는 결정론적 층**으로 옮겼다.
