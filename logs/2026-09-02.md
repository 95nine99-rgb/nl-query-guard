## 오늘의 판단

**⑧ LLM이 user_id를 쓰면 → 거부한다**
프롬프트에서 금지하므로, 어긴 출력은 LLM 오작동이거나 프롬프트 인젝션이다.
**거부는 사용자 응답이 아니라 재생성 신호다.** 사용자에게 에러가 나가지 않는다.

**⑨ WHERE가 없으면 → 주입한다**
정규식 버전이 거부했던 것은 **처리할 수 없어서**였다. 능력의 한계지 정책이 아니었다.
"거래내역 다 보여줘"는 정상 요청이다.

**④ 테스트 DB 의존 → CI에 MySQL service**
Testcontainers가 더 낫지만(로컬·CI 동일 동작) 학습 비용 때문에 P2로 미뤘다.
`contextLoads()` 제거는 버렸다. 8/31에 DataSource 자동설정이 두 번 깨졌는데
**컴파일도 되고 단위 테스트도 통과한다.** 기동해야만 드러나는 계열을 영영 못 잡게 된다.

### 판단

**ADR-001 확정: C안 (LLM 이 SELECT 전체 생성)**
프롬프트가 B안(WHERE 조각) 기준이라 충돌했다. C안으로 다시 썼다.
B안은 안전하지만 **검증할 SQL 자체가 없어져 프로젝트 주제가 사라진다.**

**Spring AI 를 안 쓴다**
`LlmClient` 포트를 직접 만든다. Spring AI 가 해주는 일을 직접 해보는 것이 학습 목적에 맞고,
Spring Boot 4.1 호환성 위험도 피한다. `06-retro.md` 남은 과제로 기록.

**모델은 `qwen2.5:3b`**
메모리 16GB / 디스크 13GB 여유. 7B 는 디스크가 빠듯하다.
성능이 낮은 것이 오히려 재료다. **완벽한 모델을 쓰면 검증층의 존재 이유가 안 보인다.**

### 오후의 발견

**① 첫 호출부터 프롬프트 규칙을 어겼다**
"세미콜론을 쓰지 않는다" → `... LIMIT 5;`
**프롬프트는 계약이지 보장이 아니다.**

**② 프롬프트 예시에 있는 질의로 측정할 뻔했다**
"가장 비싼 거래 5건" 은 예시에 그대로 있었고, 출력이 예시와 글자 하나 다르지 않았다.
**생성이 아니라 복사였다.** 예시에 없는 질의로 바꾸자 실제 동작이 드러났다.
→ 오늘 세 번째 측정 설계 오류.

**③ LLM 이 만든 SQL 이 내 방어의 구멍을 드러냈다**
```sql
WHERE amount > 30000 AND category_id IN (SELECT id FROM categories WHERE name = '쇼핑')
```
`InExpression` 은 `BinaryExpression` 이 아니라 재귀에서 빠진다.
`WHERE user_id IN (SELECT 2)` 가 탐지를 통과했다.

**8/31 에 직접 짠 악의적 SQL 12종에는 `IN` · `BETWEEN` 이 없었다.**
책상에서 만든 목록보다 실제 사용이 넓었다.

**④ 내 재귀가 블랙리스트였다**
타입을 하나씩 나열하고 모르면 통과시키는 구조.
같은 파일 안의 `instanceof Select` 는 화이트리스트인데 **방식이 섞여 있었다.**
→ 파싱 후 문자열 검사로 통일. 코드는 2줄, 주석은 25줄.

### 데이터 유출은 없었다

구멍이 뚫린 상태에서도 `user_id = 1 AND user_id IN (SELECT 2)` 로 주입은 작동했다.
**실패한 것은 차단이 아니라 계약 위반 탐지다.** 심각도를 정확히 매겨야 한다.
