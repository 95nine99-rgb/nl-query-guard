## 오늘의 발견

**① 옵티마이저가 복합 인덱스를 안 골랐다**
`idx_tx_user_cat_time` 을 만들고 `ANALYZE TABLE` 까지 했는데도 `fk_tx_category` 를 골랐다.
`FORCE INDEX` 로 재보니 읽는 행이 995 → 20 으로 줄고 `Sort` 단계가 사라졌다(1.62ms → 1.20ms).
원인은 **시드 유저가 3명이라 `user_id` 카디널리티가 3**이었기 때문.
`EXPLAIN` 만 봤으면 "인덱스가 소용없다" 로 잘못 결론 낼 뻔했다.

**② 파서 0줄로 12종 중 8종이 막혔다**
읽기 전용 계정 하나로. 코드는 한 줄도 안 짰다.

**③ 뚫린 4종은 DB 가 구조적으로 막을 수 없다**
5·7·11 은 `transactions` 를 `SELECT` 하는 정상 요청이다. **DB 는 "누구 것인지" 를 모른다.**
권한 경계는 앱에서만 강제할 수 있다는 게 측정으로 정의됐다.

**④ 방어층 4가 두 갈래였다**
`DROP` 을 `query_ro` 로 쳤을 때 MySQL 권한(4b)이 아니라 **JDBC `readOnly`(4a)가 먼저 잘랐다.**
4a 는 코드 한 줄로 무력화되고 4b 는 안 된다. "막혔다" 로 끝내면 이 차이를 모른다.

**⑤ 예외가 원인을 감췄다**
`query_ro` 로 `SELECT * FROM users` → Spring 이 `BadSqlGrammarException` 으로 감쌌다.
진짜 원인은 문법이 아니라 **권한 거부(ERROR 1142)**. MySQL 이 권한 오류를 SQLState 42000 으로 내려서 생긴 혼동.
예외 체인 끝까지 따라가는 `rootMessage()` 를 넣고서야 드러났다.

## 막힌 것

- **측정 순서를 잘못 짜서 첫 결과가 오염됐다.** 1번(`DROP`)을 먼저 돌려 2~9번이 `TABLE_NOT_FOUND`.
  차단으로 읽었으면 차단율 92% 가짜 결과. → 파괴형을 맨 뒤로, 매번 복구하도록 수정
- **Spring Boot 자동 설정 함정에 두 번 걸렸다.** DataSource, JdbcTemplate 둘 다.
  같은 타입 빈을 직접 만들면 자동 설정이 통째로 물러난다는 걸 몰랐다
- `SEL/**/ECT` 주석 분할은 **MySQL 에서 아예 안 통한다.** 확인 없이 표에 넣을 뻔했다
