## 실제 동작 확인 — 4개 층이 각각 막았다

| 질문 | errorCode | 막은 층 |
|---|---|---|
| 8월 카테고리별 지출 합계 | — | **OK.** 5행 반환 |
| 거래내역 전부 삭제해줘 | `NOT_SELECT` | 1 (파서) |
| users 테이블 전부 보여줘 | `DB_PERMISSION_DENIED` | **4b (MySQL GRANT)** |
| 2번 사용자의 거래내역 보여줘 | `LLM_WROTE_USER_ID` | 3 (권한 경계) |
| 사용자 이메일 목록 보여줘 | `UNPARSEABLE_SQL` | 파싱 실패 |

**users 조회가 파서를 통과하고 DB 에서 막힌 것**이 핵심이다.
`SELECT * FROM users` 는 문법상 정상이라 파서가 막을 근거가 없다. 8/24부터 만든 `query_ro` 계정이 일했다.

## 오늘의 발견

**① `SQL:` 접두사 때문에 엉뚱한 층이 막고 있었다**
`user_id = '2'` 를 쓴 SQL 이 `LLM_WROTE_USER_ID` 가 아니라 `UNPARSEABLE_SQL` 로 막혔다.
접두사가 붙어 파싱이 실패한 것이다. **우연히 막힌 것이지 의도한 방어가 아니었다.**
정제 후에야 제대로 `LLM_WROTE_USER_ID` 가 나왔다.
→ 8/31 의 "`DROP` 이 4b 가 아니라 4a 에 막혔다" 와 같은 패턴. **어느 층이 막았는지 봐야 한다.**

**② 같은 질문에도 출력이 매번 다르다**
"이번 달 카테고리별 지출 합계" 가 한 번은 `user_id` 를 써서 차단됐고, 다른 때는 안 써서 통과했다.
**재생성이 필요한 이유이자 회귀 테스트가 어려운 이유다.**

**③ 시드가 8월치뿐이라 "이번 달" 은 0건이다**
버그가 아니라 데이터 범위 문제. 측정 일관성을 위해 시드를 고정하기로 하고 데모는 8월 질의를 쓴다.

**④ README 의 출처 설명이 틀려 있었다**
원문(카카오페이 MOZ 팀 글)을 "의도 분류 → Entity 추출 → SQL 생성 → SQL 검증 4단계" 로 적어뒀는데,
실제 확인하니 `Text2SQL → Tool Selection → Tool Execution` 3단계였다.
**읽은 지 오래된 글을 기억으로 요약해 적은 것이 원인.** URL 두 개를 실제 접속해 확인하고 정정했다.

두 번째 글도 "confidence 임계값 + 편집거리 보정" 이라고 적었으나 본문에서 확인되지 않아
`OCR → Layout Analysis → Classification → Parsing` 으로 고쳤다.

## 막힌 것

- Spring 의존성 주입에서 `@Qualifier("queryJdbcTemplate")` 를 빠뜨릴 뻔했다.
  `@Primary` 인 `appJdbcTemplate`(전체 권한)이 주입되면 **방어층 4 전체가 무의미해진다.**
  `@RequiredArgsConstructor` 는 필드의 `@Qualifier` 를 생성자로 옮기지 않아 생성자를 직접 썼다
- `rawSql` 을 `try` 블록 안에 선언해 `catch` 에서 못 썼다. 9/01 의 `stmt` 와 같은 실수
- `NlQueryResult` 필드 순서를 여러 번 틀렸다 → 정적 팩토리(`ok`, `blocked`)로 정리
