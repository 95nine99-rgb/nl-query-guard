## 오늘 내린 판단
- **응답 DTO 사용.** 엔티티 직접 반환하면 LAZY 프록시 직렬화 문제 + 엔티티 변경이 API 스펙에 샌다
- **`userId`는 Request DTO에 넣지 않는다.** Request 는 클라이언트가 보낸 값이고 `userId` 는 서버가 아는 값이다.
  한 객체에 섞으면 "뭘 믿을 수 있는지" 가 흐려진다.
  → 내일모레 LLM 이 만든 SQL 에 서버가 `user_id` 를 강제 주입하는 구조와 **같은 경계**다
- **`categoryName` 을 응답에 포함 → N+1 발생 상태로 둔다.**
  fetch join 으로 지금 고칠 수 있다는 걸 알지만 **의도적으로 미룬다.**
  8/27 fetch join before/after 측정의 before 재료로 쓴다.
  카테고리가 5종뿐이고 1차 캐시가 있어 실제 추가 쿼리는 5회 안팎으로 예상 — 그 수치 자체를 내일 확인한다.
  `spring.jpa.show-sql=true` 를 켜뒀다.
