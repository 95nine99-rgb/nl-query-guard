## 오늘의 판단

**① 검사할 것인가 고쳐쓸 것인가 → 고쳐쓰기**
검사는 위험 패턴을 전부 알아야 한다. 고쳐쓰면 LLM 이 뭘 쓰든 무관하다.

**② LLM 에게 어디까지 맡길 것인가 → C안(SELECT 전체)**
WHERE 조건만 맡기면 안전하지만 **검증할 SQL 자체가 없어져 프로젝트 주제가 사라진다.**
`nl-query-guard` 인데 guard 할 대상이 없어진다.

**③ 정규식 vs 파서 → 파서**
숫자는 4:4 로 같았다. **실패의 성격이 결정적이었다.**
정규식은 SQL 을 부수고 정상 요청을 거부했다. 파서는 0건을 반환할 뿐이다.

## 오늘의 발견

**① 정규식은 변형을 하나 발견할 때마다 분기가 하나씩 늘었다**
`\s*` → 주석 제거 → `user_id` 유무 분기 → 문자열 리터럴은 **결국 포기**.
파서는 `parse()` 한 번으로 이 변형들이 사라진다.

**② 문자열 리터럴 안의 `--` 를 잘라 SQL 을 부쉈다**
`WHERE title = '스타벅스--강남점'` → `WHERE title = '스타벅스`
정규식은 문자열 안인지 SQL 구조인지 구분하지 못한다. **고치려면 결국 파싱이 필요하다.**

**③ 방어층 1이 한 줄이 됐다**
`if (!(stmt instanceof Select))` 로 DROP·DELETE·UPDATE 가 전부 막힌다.
정규식이면 위험 키워드를 나열해야 했고 빠뜨리면 뚫린다.

**④ 테스트가 출력 형식에 묶여 있었다**
구현을 갈아끼우자 4개가 공백 때문에 실패했다. 기능 문제가 아니었다.

**⑤ 가짜 통과가 있었다**
`doesNotContain("user_id = 2")` 가 공백 때문에 절대 실패하지 않는 검사였다.
고치자 실패가 하나 늘었다. **정직해진 것이다.**
